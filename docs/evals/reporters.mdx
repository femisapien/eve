---
title: "Reporters"
description: "Ship eval results to Braintrust, Datadog, or JUnit XML. eve runs and scores everything itself."
---

`eve eval` prints a console summary by default. To export results, add a reporter from `eve/evals/reporters` to `evals.config.ts` for the whole run or to individual evals for selected cases. Confirm that each destination is approved to receive the data you export.

## Braintrust

`Braintrust(...)` uploads eval results to Braintrust experiments. Put one instance in the config so it covers the whole run:

```ts title="evals/evals.config.ts"
import { defineEvalConfig } from "eve/evals";
import { Braintrust } from "eve/evals/reporters";

export default defineEvalConfig({
  judge: { model: "typesafe-ai/jev" },
  reporters: [Braintrust({ projectName: "weather-agent" })],
});
```

To report only selected evals, attach the reporter to each eval:

```ts title="evals/brooklyn-forecast.eval.ts"
import { defineEval } from "eve/evals";
import { Braintrust } from "eve/evals/reporters";

export default defineEval({
  reporters: [Braintrust({ projectName: "weather-agent" })],
  async test(t) {
    await t.send("What is the weather in Brooklyn?");
    t.succeeded();
  },
});
```

The reporter config takes an optional `projectName` and `experimentName`, plus a base experiment (by name or id) to diff against. Gate assertions log as binary scores under a `gate:` prefix so experiments diff gate regressions the same way they diff soft-score regressions. Assertions that share a name, such as several unlabeled judges, log one score: the lowest. Use `.label(name)` to group or separate them. Each assertion's score is stored in the Braintrust metadata under `eveAssertionScores` and failed assertion details under `eveFailedAssertions`; observed traces are stored under `eveTraceIds` and `eveTraceContexts`.

A reporter instance observes the evals that reference it. Share one instance across several evals (the config, a `shared.ts` export, or every entry of a dataset array) and their results land in a single experiment. Listing the same config reporter on an eval too does not double-report it.

Braintrust needs its SDK installed in the app and credentials in the environment: install the `braintrust` package (`npm install braintrust`) and set `BRAINTRUST_API_KEY`. Pass `--skip-report` to run the eval without shipping results, which also suppresses config reporters and is useful locally when iterating.

## Datadog

`Datadog(...)` uploads eval assertion scores to a Datadog LLM Observability Experiment. Put one instance in the config so it covers the whole run:

```ts title="evals/evals.config.ts"
import { defineEvalConfig } from "eve/evals";
import { Datadog } from "eve/evals/reporters";

export default defineEvalConfig({
  reporters: [Datadog({ projectName: "weather-agent" })],
});
```

The reporter creates one Datadog Experiment with an assertion-score span per completed eval. By default, `recordInputs` syncs a versioned dataset after the evals finish, links each span to its dataset record, and prints both URLs. With `recordInputs: false`, it uses a placeholder dataset, submits spans as evals finish, and prints the Experiment URL. These spans are separate from the agent runtime's OpenTelemetry spans.

Every run reuses the dataset named by `datasetName` (default `<projectName> evals`), so Datadog can compare experiments across runs. Records are matched by eval description, with `#2`, `#3` suffixes for duplicates, so give each case a unique description.

By default, Datadog metrics use assertion names. Characters other than letters, numbers, underscores, and hyphens become underscores; gate labels get a `gate_` prefix. Assertions sharing a label report one metric with the lowest score, and labels colliding with built-in metrics get a numeric suffix. For example, `succeeded` becomes `gate_succeeded` and `calledTool(get_stock_quote)` becomes `gate_calledTool_get_stock_quote`. Use `.label("stable name")` on an assertion handle to choose a stable name.

Assertion names can contain authored expectations; review them before exporting sensitive evals. Row metadata stores each name and score under `eveAssertionScores`. Pass `recordAssertionDetails: false` to omit those details and failed assertion messages.

Install `dd-trace` in the app (`npm install dd-trace@6.13.0`, the tested version) and set `DD_API_KEY`, `DD_APP_KEY`, and `DD_SITE` as appropriate. Reporting is skipped without credentials. By default, the reporter records eval prompts, outputs, authored expectations, and execution error messages. If the destination is not approved for that content, pass `recordInputs: false`, `recordOutputs: false`, `recordExpectedOutputs: false`, or `recordErrors: false`.

With `recordInputs`, the reporter stores the first `t.send(...)` input in the linked dataset record and experiment span; it falls back to the eval description when no message event is available. With `recordExpectedOutputs`, it stores eval `metadata.expectedOutput`, `metadata.expected`, or `metadata.expected_output` in both places. A dataset record without an authored expected output is still valid. Those keys are excluded from the general metadata payload. Target URL credentials, paths, query parameters, and fragments are never reported.

## JUnit

`JUnit({ filePath })` writes JUnit XML for CI annotations. The `--junit <path>` CLI flag does the same thing without touching the eval file, usually the better fit because CI owns the output path, not the eval:

```bash
eve eval --strict --junit .eve/junit.xml
```

Each eval becomes one `<testcase>` named by its path-derived id; failed gates and execution errors become failures, while `t.skip(reason)` produces a JUnit `<skipped>` result.

## Custom reporters

A reporter implements the `EvalReporter` interface from `eve/evals/reporters` and receives the same structured results the built-ins do. Every callback may return a promise for async work like a remote upload:

```ts
interface EvalReporter {
  onRunStart(evaluations: readonly EveEval[], target: EveEvalTarget): void | Promise<void>;
  onEvalStart?(event: EveEvalStartEvent): void | Promise<void>;
  onSessionStart?(event: EveEvalSessionStartEvent): void | Promise<void>;
  onEvalComplete(result: EveEvalResult, context?: EveEvalCompleteContext): void | Promise<void>;
  onRunComplete(summary: EveEvalRunSummary): void | Promise<void>;
}
```

`onRunStart` fires once before any eval runs, and `onRunComplete` fires once with the aggregated summary. Within that run:

- `onEvalStart` fires when an eval is scheduled. It includes the eval definition, target, and start time.
- `onSessionStart` fires once for each session after eve receives its first trace context. It includes `sessionId`, `primary`, and `traceContext` with `traceId`, `spanId`, and `traceFlags`.
- `onEvalComplete` fires with the checks, scores, and verdict. The runner also supplies `context`, including every distinct trace context collected across the eval's sessions. The same list is available as `result.result.traceContexts`.

An eval can create several sessions, and a long session can produce several traces, so completion exposes a list instead of a single trace id. `onEvalStart` does not include a trace because the agent session has not started yet. If the target has no tracing configured, `onSessionStart` does not fire and the completed trace list is empty.

`result.result.derived` holds the facts the runner derived from the eval's sessions, such as tool calls and `models`: the distinct ids of the models the steps started with, in session order. Each entry in `result.result.sessions` holds the same facts for one session, in first-use order, so a reporter can tell the primary session's models from those of the other sessions the eval created or attached. A delegated subagent runs in its own session, so its models appear only when the eval attaches that session with `t.target.attachSession`. Compaction and `auto` routing calls are not included.

`derived.usage` is the token usage and cost from each session's latest `session.waiting`, `turn.waiting`, `session.failed`, or `session.completed`, including what its delegated agents spent; on a turn, it is the session's total so far. The eval's `usage` counts each captured session once, by its latest usage, and leaves out sessions another captured session opened, because that session already counts their spend. It is absent when a counted session reported no usage. It leaves out compaction calls, the turns an eval sends directly to a child session it attached, and delegated spend counted after a session's last such event.

Reporter callbacks for an eval stay ordered—start, traced sessions, completion—even when evals run concurrently. Per-run artifacts under `.eve/evals/` retain trace contexts for inspection.
